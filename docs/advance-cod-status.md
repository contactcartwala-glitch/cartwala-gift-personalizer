## Implemented in this review

- Authenticated `/app/advance-cod` admin page and navigation.
- Store-specific settings, disabled by default, and whole advance percentages from 10 to 50.
- A fixed INR 80 charge paid upfront. An INR 1,000 product total at 20% means INR 280 now and INR 800 on delivery.
- Optimistic settings revision checks to reject stale saves from another admin tab.
- Integer-paise calculations with nearest-paise rounding, including database amount constraints.
- Each intent stores its own percentage; payment verification and courier amounts use that frozen percentage.
- Signed app-proxy `/signature-day/partial-cod` configuration and review-quote endpoint. The corresponding storefront URL is `/apps/cartwala-signature-day/partial-cod`.
- Shopify-calculated prices and tax; artwork properties and validated Indian addresses are retained in the review intent. Automatic discounts are detected but rejected before payment until their per-line allocations can be preserved exactly.
- Quote requests are explicitly review-only, single-use, bounded in size, and reject discount codes until customer eligibility is implemented.
- Server-side activation gates reject enabling the incomplete integration, even if the admin form or environment is modified.

## Single-order accounting candidate added 5 November

Each review quote now freezes a versioned accounting snapshot: exact variant/unit prices, quantities, stable line UUIDs, personalization attributes, shipping/taxability flags, tax-included mode and tax lines including channel liability. Line UUIDs match the server-calculated draft even if returned lines are reordered. Discounts, bundles, gift cards, missing/changed lines and unreconciled amounts fail before payment. Old quotes without snapshots cannot claim a Paytm checkout. The nullable snapshot migration is not deployed.

The order candidate contains merchandise once plus a non-shipping INR 80 fee, with one SUCCESS/SALE transaction recording only the already-verified Paytm advance. It omits financialStatus so Shopify must derive the actual partially-paid state; no second deposit order or legacy outbox is used. The fee is currently represented as non-taxable; its production tax treatment and Shopify's interpretation must be checked in the merchant's actual setup before activation. The adapter cannot silently change the frozen total to accommodate differences.

The offline-app worker first re-verifies the Paytm transaction and zero-refund status, commits a unique durable order claim, and calls orderCreate once with SDK tries=1, inventory decremented only if available, and customer receipts disabled. It records the candidate order ID before a separate paginated read verifies exact merchandise/artwork, delivery details, exclusion tag, taxes, advance received and remaining balance. Only a successful acknowledgment links the local COD order. Unknown outcomes/rejections cannot trigger another POST. An uncertain attempt can adopt the original matching Shopify order after read-only verification, without creating another sale. Processing attempts interrupted by a worker crash still require operator triage before recovery; automatic stale-worker takeover is not implemented. These migrations have not run in production.

Every order creation, including staging, requires an explicit automatic-shipping-sync exclusion. The internal runtime uses the configured shop's own offline Admin client; it never takes shop credentials from a public request. Production creation remains gated off. The callback is deliberately not wired to dispatch this worker yet, and no initiation route is exposed. The external ADVANCE_COD_SHOPIFY_SYNC_EXCLUDED flag has not been set or verified.

## Checkout and recovery implementation

- App-proxy create_quote returns a signed, seven-day capability bound to the authenticated shop and persisted quote. Review-only quotes never return checkout access. Initiation rechecks settings, provider binding, quote expiry and accounting snapshot; only one durable claim reaches Paytm. Status operations do not accept browser amount/status/transaction proof.
- The cart block preserves variant quantities/artwork, gathers an Indian delivery address and displays the exact upfront fee, advance and balance. It blocks repeated clicks immediately, keeps only the recovery capability in sessionStorage, and never persists the Paytm transaction token or address there. An existing capability resumes status checks after refresh even when new checkout is disabled. If refreshed before payment starts, it asks the merchant to review rather than silently paying an old cart. Mobile popup behavior still needs a real staging browser test.
- Callback, customer recovery and merchant recovery use one server-verification path. A successful provider re-read records proof, then dispatches the single-order worker. Shipping exclusion and production readiness apply to creation/reconciliation. A processing claim older than 90 seconds becomes uncertain, never reusable. A saved order candidate is re-read, never re-posted; an unknown candidate must be found and verified by the merchant.
- /app/advance-cod-recovery lists up to 25 oldest unresolved checkouts, scoped to the signed-in shop, without customer/address fields. It rechecks payment and can adopt an original Shopify order only after exact payment/accounting/artwork/address verification. It cannot refund, replace an order or book a shipment.
- POST /api/advance-cod-recovery requires a separate COD_RECOVERY_JOB_TOKEN of at least 32 bytes. It takes no shop, amount, intent ID or credential from the caller, reads at most 10 eligible attempts, uses two workers and emits counts only. Scheduling and secure token configuration remain deployment tasks. No scheduler was created and no new environment values were saved.
- New PostgreSQL tests model Prisma typed-text parameters and cover signed capability tampering, expiry, cross-shop/account checks, twelve concurrent starts/status checks, pending/failed/provider-error/paid paths, held dispatch and closed intents. Storefront tests cover amounts, artwork, twelve-click duplicate blocking, script initialization, token storage, spoofed callback status, reload recovery and disabled/storage guards. Recovery-job HTTP tests reject missing/wrong tokens and sanitize provider errors. Existing COD/diagnostic suites, scoped ESLint, typecheck and production build pass. No provider mutation was run for these tests.
- Shopify Toolkit theme/component validation could not execute because the installed tool bundle lacks _validate_theme.mjs and _validate_components.mjs. This is an outstanding validation limitation, not a pass. Actual Liquid/extension publish validation and visual QA must run before release.

## Refund proof verification added

The draft now includes server-only full-advance refund reference construction and signed Paytm refund-status verification. The stable 50-character reference binds shop, intent, original Paytm transaction, merchant and environment. A success requires TXN_SUCCESS / code 10 and exact original transaction amount, refund amount and cumulative amount equal to the advance actually collected, including the COD fee. Partial, excessive, mismatched, missing and tampered evidence cannot produce refunded proof. Pending, failed and missing-record states do not prove a refund and never authorize resubmission. Provider destination/card/bank/phone details are not returned. SDK-signature tests and scoped typecheck/ESLint pass. No HTTP refund submission or real financial operation occurred.

This is a verification component, not complete cancellation/refund handling. Durable refund claims, serialized cancellation/order-creation holds, Shopify cancellation/accounting reconciliation, NimbusPost shipment cancellation acknowledgment and merchant-confirmed refund execution/recovery remain required before the refunds readiness gate can change. The current documentation exposes different refund endpoint families across examples, so the actual account-compatible endpoint must be confirmed in staging rather than guessed or silently substituted.
