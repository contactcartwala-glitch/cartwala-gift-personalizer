# Advance COD review: updated 5 November 2026

## Implemented in this review

- Authenticated `/app/advance-cod` admin page and navigation.
- Store-specific settings, disabled by default, and whole advance percentages from 10 to 50.
- A fixed INR 80 charge paid upfront. An INR 1,000 product total at 20% means INR 280 now and INR 800 on delivery.
- Optimistic settings revision checks to reject stale saves from another admin tab.
- Integer-paise calculations with nearest-paise rounding, including database amount constraints.
- Each intent stores its own percentage; payment verification and courier amounts use that frozen percentage.
- Signed app-proxy `/signature-day/partial-cod` configuration and review-quote endpoint. The corresponding storefront URL is `/apps/cartwala-signature-day/partial-cod`.
- Shopify-calculated prices and tax; artwork properties and validated Indian addresses are retained in the review intent. Automatic discounts are detected but rejected before payment until their per-line allocations can be preserved exactly.
- Quote requests are explicitly review-only, single-use, bounded in size, and reject discount codes until customer eligibility is implemented.
- Server-side activation gates reject enabling the incomplete integration, even if the admin form or environment is modified.

## Still incomplete

This is not a functioning paid checkout. The review endpoint never creates a payment, invoice, merchandise order or shipment. Existing theme cart-review snippets still show the original 20% illustration; they are not connected to the configurable setting.

The older deposit-order approach is not used by the new Paytm path: recording a separate deposit sale and full-value merchandise order would duplicate sales. Native Shopify draft-order deposits are limited to Plus; this store is Basic. The draft now has a single-order candidate described below, but an actual offline-app Shopify accounting test is still required before activation.

NimbusPost account inspection confirmed that the Shopify channel is active. A dedicated `Cartwala Advance COD` Admin API key was created with merchant approval, with PII access disabled. A read-only `/v2/couriers` request succeeded (HTTP 200, `success: true`). Credentials are private and are not committed to the repository; the new server credentials have now been saved to Render as described below; a backend redeploy and authentication test remain pending.

The new NimbusPost v2 adapter maps the frozen remaining amount to `order_collectable_amount`, converts paise to rupees, sends parcel weight in kilograms and phone/pincode as numbers. It refuses unverified payment states, unreconciled merchandise values and orders whose automatic Shopify shipping sync has not been excluded. It creates an unbooked order only, never books or requests pickup, requires a separate provider order re-read to acknowledge the exact balance, and never automatically repeats an uncertain POST. This adapter is not connected to the checkout or outbox yet. Mocked tests verify mapping and error recovery, not a live COD order acknowledgment. No courier order or shipment was created.

The page was reloaded to verify both variable names persisted. No secret value is committed here, and the running build has not been redeployed to consume these variables.

The server-only Paytm adapter uses the pinned `paytmchecksum` 1.5.1 SDK for request signing and response verification, separate fixed staging/production hosts, server-frozen amounts and an opaque stable reference per shop/intent. A successful signed transaction-status re-read must acknowledge the merchant, order, exact amount, transaction ID, successful capture and zero refunded amount. Pending/failed responses do not produce paid proof. Production initiation requires an explicit opt-in and does not retry requests automatically. No initiation route is exposed, so it cannot currently collect a payment. A bounded POST callback route now verifies the form signature, binds the persisted reference to the configured shop/merchant/environment, and re-reads signed provider status before recording any proof. A callback never supplies payment proof directly.

The draft now includes `PartialCodPaytmAttempt`, its migration, and a parameterized SQL payment store. It commits a single-writer claim and moves the quoted intent to awaiting payment before reaching Paytm, rejects expired quotes and mismatched account/amount references, keeps uncertain calls for reconciliation without sending another initiation, and records repeated paid proof idempotently. A unique provider fingerprint prevents using one transaction for two intents. Transaction tokens are not persisted. Recording Paytm proof deliberately does not enqueue the old deposit-order outbox or mark a Shopify order paid. The Prisma query bridge and callback route are implemented in the draft. The callback has a database-backed status-check lease to limit signed replays across workers, rejects unsupported methods/media types and oversized bodies, and returns generic responses without logging provider errors or customer details. It requires explicit PAYTM_SHOP and PAYTM_ENVIRONMENT bindings in addition to the saved credentials; these bindings are not configured yet. Status-recovery UI/job and refund/cancellation recovery remain incomplete. A single-order accounting worker and local recovery functions are now implemented as described below; actual Shopify mutation behavior remains unverified. This migration has not run on production.

## Single-order accounting candidate added 5 November

Each review quote now freezes a versioned accounting snapshot: exact variant/unit prices, quantities, stable line UUIDs, personalization attributes, shipping/taxability flags, tax-included mode and tax lines including channel liability. Line UUIDs match the server-calculated draft even if returned lines are reordered. Discounts, bundles, gift cards, missing/changed lines and unreconciled amounts fail before payment. Old quotes without snapshots cannot claim a Paytm checkout. The nullable snapshot migration is not deployed.

The order candidate contains merchandise once plus a non-shipping INR 80 fee, with one SUCCESS/SALE transaction recording only the already-verified Paytm advance. It omits financialStatus so Shopify must derive the actual partially-paid state; no second deposit order or legacy outbox is used. The fee is currently represented as non-taxable; its production tax treatment and Shopify's interpretation must be checked in the merchant's actual setup before activation. The adapter cannot silently change the frozen total to accommodate differences.

The offline-app worker first re-verifies the Paytm transaction and zero-refund status, commits a unique durable order claim, and calls orderCreate once with SDK tries=1, inventory decremented only if available, and customer receipts disabled. It records the candidate order ID before a separate paginated read verifies exact merchandise/artwork, delivery details, exclusion tag, taxes, advance received and remaining balance. Only a successful acknowledgment links the local COD order. Unknown outcomes/rejections cannot trigger another POST. An uncertain attempt can adopt the original matching Shopify order after read-only verification, without creating another sale. Processing attempts interrupted by a worker crash still require operator triage before recovery; automatic stale-worker takeover is not implemented. These migrations have not run in production.

Every order creation, including staging, requires an explicit automatic-shipping-sync exclusion. The internal runtime uses the configured shop's own offline Admin client; it never takes shop credentials from a public request. Production creation remains gated off. The callback is deliberately not wired to dispatch this worker yet, and no initiation route is exposed. The external ADVANCE_COD_SHOPIFY_SYNC_EXCLUDED flag has not been set or verified.

Validation: all five COD migrations used by the order path run in embedded PostgreSQL. The new order suite covers 10/20/30/40/50% accounting, tax-inclusive/exclusive values, frozen prices/artwork and reordered line UUIDs, old/unsupported quote rejection, a single order mutation across 12 overlapping calls, completed-call idempotency, no legacy deposit outbox, uncertain/lost-response recovery without re-POST, explicit rejection, pending/closed payments, cross-shop protection, shipping-sync/live gates and 101 line items read over three pages. Shopify HTTP is mocked in this suite; it does not prove that the live API will accept the imported partial payment.

An actual draftOrderCalculate request against Cartwala's existing INR 300 baby-frame variant returned INR 300 merchandise, zero shipping/discount/tax, tax-included mode, matching line UUID and preserved property. The real response passed the snapshot validator. This calculation creates no draft order, order, payment or shipment. Header/line-read field selections also passed the connected API's schema validation using an empty COD-tag search. The local Shopify Toolkit validator was attempted for all four GraphQL operations but could not run because its bundled schema assets are unavailable; this is not a validation pass. Full app typecheck/build and changed-module ESLint pass; an actual orderCreate through the offline app and provider staging tests remain outstanding.
